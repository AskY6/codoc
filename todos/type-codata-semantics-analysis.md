# .codoc `type` 字段的 Codata 语义评估

## 评估对象

`m3-demo.codoc` 中的五个字段，覆盖了全部四种 loader 类型。

## 逐字段 Codata 语义验证

| 字段 | Loader 类型 | Force 过程 | Codata 语义 |
|---|---|---|---|
| `title` / `mode` | literal | 返回已有值，成本为零 | 退化情况，合法。值因观察而产生，只是产生过程是瞬时的 |
| `derived` | `$ref` | 解析 `/title`，建立 title -> derived 依赖边 | 经典公式引擎场景，完全符合 |
| `todo` | `$source` | HTTP 请求 + 30s TTL 缓存 | 核心价值体现：不是"值还没到"(Promise)，而是"你问我才去拿"(codata)。无人观察则请求不发 |
| `aiSummary` | `$prompt` | force 依赖(title, mode) -> 拼 prompt -> 调 LLM -> 返回结果 | 最典型的 codata：无人观察则 LLM 调用不发生（语义正确，非优化）；每次 force 可能返回不同结果（无限性） |

结论：四种 loader 类型全部符合 codata 的三个核心性质：

1. **接口先于内容** — type 声明了 schema，消费者（view）不关心值怎么来的
2. **惰性求值** — 值因观察而产生，特别是 `$source` 和 `$prompt` 不被观察就不会执行
3. **可以是无限的** — `$prompt` 每次 force 可能返回不同结果；`$source` 随外部数据变化

## 发现的问题：type 声明过薄

### 现状

```yaml
type:
  properties:
    title:
      type: string
    aiSummary:
      type: string
```

当前 `type` 只声明了两层信息：**字段存在** + **数据类型**。

### 缺失

Codata 的"接口先于内容"要求消费者仅凭 type 就能理解字段"能回应什么观察"。当前 type 无法做到这一点。

具体来说，一个 Agent 读到 `aiSummary: { type: string }` 时，它知道这个字段是 string，但不知道：
- 这个字段的语义是什么（文档摘要？标题翻译？情感分析？）
- 它依赖哪些其他字段
- 观察它的成本如何（literal 近乎零，$prompt 需要调 LLM）

### 对已有代码的影响

`CodataMeta` 中已经预留了 `description?: string` 字段（`types.ts:39`），但 `.codoc` 的 type section 没有使用它。从 parse 到 registry 的链路中，description 没有从 type 声明中提取。

## 改进方向（不改变 codata 模型，只增厚 type）

### 方案：在 type 的 property 定义中加入 description 和 metadata

```yaml
type:
  properties:
    title:
      type: string
      description: "Document title, used as display heading and AI prompt input"
    mode:
      type: string
      description: "Runtime mode flag (demo/production)"
    todo:
      type: object
      description: "External TODO item fetched from REST API"
      costHint: async          # 提示消费者：观察此字段有 IO 成本
    derived:
      type: string
      description: "Mirror of title via internal reference"
    aiSummary:
      type: string
      description: "One-sentence summary generated by LLM based on title and mode"
      costHint: expensive       # 提示消费者：观察此字段有 LLM 调用成本
```

### 三层递进的 type 厚度

| 层级 | 信息 | 消费者能做的决策 | 当前状态 |
|---|---|---|---|
| L0 | 字段存在 + 数据类型 | "这个字段是 string" | 已实现 |
| L1 | + description | "这个字段是文档摘要，我需要/不需要它" | CodataMeta 有位置，type section 未使用 |
| L2 | + costHint / dependencies | "观察它很贵，我先判断是否真的需要" | 未实现 |

L1 是最小有价值改动，直接提升 AI 友好性。L2 可延后到 M5+ 按需引入。

## 结论

1. **M3 验证用例合格** — 四种 loader 类型齐全，依赖关系清晰，view 作为纯观察者消费 codata
2. **Codata 模型正确** — 三个核心性质在 m3-demo.codoc 中都有对应
3. **Type 声明需要增厚** — 当前只到 L0，至少应做到 L1（加 description），以兑现"接口先于内容"的 AI 友好性承诺
4. **不需要改 codata 模型** — 这是 type schema 层面的增强，不涉及 loader、DataTree、force 等核心机制的变更

## 与其他设计的关系

- **M4 跨文档引用**（见 `m4-change-detection-design.md`）：增厚的 type 能帮助 DocResolver 在不 force 目标字段的情况下判断类型兼容性
- **Agui 消费**：Agent 可以通过 type + description 决定观察哪些字段，避免不必要的 $prompt/$source force
