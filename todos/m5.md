# M5 拆分：逻辑 Workspace + Cobook

原 M5（Workspace）拆为两层：core 中的逻辑 Workspace（M5-core）和基于逻辑 Workspace 的知识管理应用（Cobook）。拆分的本质是 infrastructure 和 application 分离——逻辑 Workspace 不知道自己被用来做什么，Cobook 是第一个消费它的应用。

---

## 一、M5-core — 逻辑 Workspace

### 定位

M5-core 是 core 的一部分，职责是让多棵 codata tree 形成可管理的依赖网络。它向上暴露通用能力，不绑定任何应用语义。

### 交付

**a. Workspace 索引**

一个 workspace 目录下所有 `.codoc` 的注册表。启动时扫描，变更时增量更新。

- 枚举 workspace 内所有 `.codoc`
- 读取每个 `.codoc` 的 meta 层（type + data schema），不 force 值
- 从 meta 中提取所有 `[[external]]` 引用声明

索引是轻量的内存结构，不是数据库。v1 不需要持久化——重启时重新扫描。

**b. 全局依赖图**

从索引中聚合所有跨文档引用，构建 workspace 级 DAG。

- 节点粒度：`docId + fieldPath`
- 边来源：`[[external.codoc]].data.field` 引用关系
- v1 中查询时从索引构建，不常驻内存
- 循环检测复用 M1 的算法，扩展到跨文档场景

**c. 跨文档标脏传播**

已加载 codoc 之间的变更传播。

- A 的字段值变了 → 沿全局 DAG 标脏所有下游字段（包括其他已加载 codoc 中的字段）
- 未加载的 codoc 不主动标脏。加载时通过上游字段的 generation counter 发现输入已过期，触发首次 force
- 标脏只做失效标记，不触发 force。Force 仍由 observe 驱动，保持 codata 惰性语义

**d. 文档生命周期管理**

- 按需加载：observe 到跨文档引用时，加载目标 codoc
- 未加载文档以 proxy 节点存在于全局图中
- v1 不做卸载策略——加载后常驻，直到 workspace 关闭

### API 边界

Workspace 向应用层暴露四个能力：

```typescript
interface Workspace {
  // 索引：枚举和读取 meta
  listDocs(): DocMeta[]
  getDocMeta(docId: string): DocMeta

  // 全局图：字段级依赖关系
  getDependencyGraph(): Graph<FieldAddress, DepEdge>

  // 文档加载：返回可 observe 的 codoc 实例
  loadDoc(docId: string): CodocRuntime

  // 变更订阅：workspace 级字段变更通知
  onFieldChange(callback: (event: WorkspaceChangeEvent) => void): Unsubscribe
}
```

`DocMeta` 只包含 type（JSON Schema）和 data 的 schema 层信息（字段名、类型、描述、引用声明），不包含值。这是 codata "接口先于内容"在 API 层的体现——消费者先读地图，再决定 observe 哪些字段。

### 不在 M5-core v1 中做的事

- 常驻内存的增量全局图维护（查询时构建够用）
- 未加载文档的标脏持久化（加载时检查够用）
- 事务性并发控制（last-write-wins + 标脏收敛够用）
- 冷启动优化（全量扫描够用）
- Workspace 外部依赖的边界处理（v1 只支持 workspace 内引用）

### 依赖

M4（需要跨文档引用的基础能力）

### 验证标准

一个 workspace 目录内 5+ 个互相引用的 `.codoc`。通过 Workspace API 获取全局依赖图，图结构正确。修改一个 codoc 的字段值，依赖它的其他已加载 codoc 中的下游字段自动标脏。

## 二、Cobook MVP — 团队知识图谱应用

### 定位

Cobook 是逻辑 Workspace 之上的第一个应用。核心价值主张：**团队的知识不是一堆文件，而是一张活的、可追溯的、自更新的计算图。**

面向团队协作场景。知识以 codoc 方式原生创建（v1 不处理非结构化文档的摄入）。

### 设计原则

**Cobook = workspace 图管理 + codoc render 的编排层。**

知识节点的内容渲染复用 codoc 自身的 MDX render engine，不另起一套 UI。Cobook 只负责图层面的交互、多文档的编排、以及在 render 结果之上叠加协作和 staleness 的元信息。

这意味着 cobook 的自有 UI 代码集中在编排和元信息，不侵入 codoc 的 view 定义。对知识呈现质量的需求会转化为 core component registry 的组件丰富度——健康的压力方向。

### 三个界面

**1. 图谱视图（Graph View）**

Cobook 的主界面。调用 `workspace.getDependencyGraph()` 渲染 workspace 内所有知识节点及其依赖关系。

- 节点展示：codoc 名称 + type 顶层 schema 摘要（字段名、类型）。用户看到的是知识的结构，不是内容。不触发任何 force
- 边展示：字段级引用关系，方向表示数据流向
- Staleness 标记：含 stale 字段的节点高亮，一眼看到"哪些知识过期了"
- 基础交互：缩放、平移、按关键词过滤节点

**2. 节点详情（Doc View）**

点击图谱中的节点，加载并渲染对应 codoc。

- 调用 `workspace.loadDoc(docId)` 获取 codoc 实例
- 交给 render engine 走标准 observe → force → MDX render 流程
- Cobook 在渲染结果之上叠加 staleness overlay：stale 字段旁标注上游变更源和时间
- 用户可手动触发 re-force（确认更新）或暂时忽略
- 依赖面板（侧边栏）：直接依赖（我引用了谁）+ 直接被依赖（谁引用了我），点击跳转

**3. 变更流（Change Feed）**

时间线视图，展示 workspace 内最近的变更事件。

- 基于 `workspace.onFieldChange()` 订阅
- 每条记录：哪个 codoc 的哪个字段变了、时间、影响的下游节点列表
- 团队成员的核心消费模式："自从我上次看以来，知识图谱里发生了什么变化"

### 不在 Cobook MVP 中做的事

- 知识节点的在线编辑（编辑走开发侧工具链或 Agent）
- 实时协同编辑
- 模板系统（竞品分析模板、会议纪要模板等）
- 推导链的完整审计日志（依赖面板只展示直接依赖，不展示完整链路的 force 历史）
- 非结构化文档的结构化摄入（所有知识以 codoc 原生创建）
- 权限控制

### 技术栈

- 图谱可视化：D3 或同类图渲染库
- 知识节点渲染：复用 core 的 render engine（MDX + React）
- 状态管理：不引入额外框架。知识节点状态在 codoc runtime 中，图谱状态从 Workspace API 查询
- Staleness overlay：React 组件层，订阅 workspace 变更事件，装饰 render 输出

### 依赖

M5-core（逻辑 Workspace 的全部能力）

### 验证标准

一个 workspace 内有 5+ 个互相引用的 codoc，覆盖字面量、`$ref`、`$source`、`$prompt` 等 loader 类型。用户打开 cobook：

1. 图谱视图正确展示所有节点和依赖边
2. 点击节点，看到该 codoc 的 MDX 渲染结果
3. 修改某个上游 codoc 的字段值，下游节点在图谱上标记为 stale
4. 打开 stale 的下游节点，看到 stale 字段的标注，手动 re-force 后内容更新
5. 变更流中出现对应的变更记录

## 三、里程碑依赖关系

```
M0 (codata 内核)
 └→ M1 (relation engine)
     └→ M2 (render + 单文档) ← Core MVP
         └→ M3 (扩展 loader)
             └→ M4 (跨文档引用)
                 └→ M5-core (逻辑 workspace)
                     └→ Cobook MVP ← 应用 MVP
```

M0–M4 不变。M5 拆为 M5-core 和 Cobook，严格串行依赖。

两层之间的边界是 Workspace API。Cobook 不绕过 Workspace 直接操作 codoc 内核——所有对知识图谱的操作都通过四个 API 入口（listDocs、getDependencyGraph、loadDoc、onFieldChange）。

核心等式仍然只有一个：`observe(codata) → force(deps) → value → propagate(dependents)`。M5-core 把这个等式从单棵 tree 扩展到多棵 tree 构成的 DAG。Cobook 是这个等式在产品侧的投射——图谱视图是依赖图的可视化，staleness 是标脏的可视化，re-force 是 observe 的用户态触发。
