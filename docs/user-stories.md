# Codoc 用户故事

> 以用户视角描述的功能验收场景。每条故事包含角色、目标、验收标准。
> 范围：Web UI + Server API，不含 CLI。

---

## 1. Workspace 管理

### US-W1 创建工作区

**作为**用户，**我想**创建一个新的工作区，**以便**将一组相关的知识文档组织在一起。

**验收标准：**
- 在首页点击创建，输入名称后成功创建
- 创建后自动跳转到该工作区详情页
- 工作区列表中出现新卡片，显示名称和创建时间
- 名称不能为空

### US-W2 浏览工作区列表

**作为**用户，**我想**在首页看到我所有的工作区，**以便**快速选择进入某个项目。

**验收标准：**
- 首页以卡片网格展示所有工作区
- 每张卡片显示工作区名称
- 无工作区时展示空状态引导

### US-W3 进入工作区详情

**作为**用户，**我想**点击某个工作区后看到它的全貌，**以便**了解其中包含哪些 codoc 和对话。

**验收标准：**
- 进入后左侧展示对话列表（按日期分组）
- 右侧展示 codoc 列表或依赖图
- 顶部显示工作区名称和操作按钮（新建对话等）

### US-W4 删除工作区

**作为**用户，**我想**删除不再需要的工作区，**以便**保持列表整洁。

**验收标准：**
- 删除前有确认提示
- 删除后从列表中消失
- 工作区下的所有 codoc、对话、依赖关系一并删除

### US-W5 查看工作区状态概览

**作为**用户，**我想**一眼看到工作区的健康状况，**以便**判断是否有需要关注的问题。

**验收标准：**
- 显示 codoc 总数
- 显示各状态（ready / dirty / error / idle）的数量分布
- error 状态有醒目标识

## 2. Codoc 文档管理

### US-C1 创建 codoc

**作为**用户，**我想**在工作区中创建一个新的 codoc，**以便**记录和组织结构化知识。

**验收标准：**
- 指定 path（如 `notes/meeting.codoc`）和 YAML 内容
- 创建成功后可在 codoc 列表中看到
- 自动触发解析，AST 入库
- path 在工作区内唯一，重复时报错

### US-C2 查看 codoc 详情

**作为**用户，**我想**查看某个 codoc 的完整信息，**以便**了解它的元数据、数据值和渲染效果。

**验收标准：**
- 右侧面板展示 codoc 详情
- 分区显示：meta 信息、resolved data（JSON）、view 渲染结果
- 显示当前节点状态（status badge：ready/dirty/error/idle）
- 加载过程中有 skeleton 占位

### US-C3 更新 codoc 内容

**作为**用户，**我想**修改已有 codoc 的内容，**以便**保持知识的时效性。

**验收标准：**
- 提交新的 YAML 内容后保存成功
- 触发增量重建：自身重新解析，下游依赖节点状态传播更新
- 更新后详情页即时反映新内容

### US-C4 删除 codoc

**作为**用户，**我想**删除不再需要的 codoc，**以便**保持工作区的精简。

**验收标准：**
- 删除后从列表中消失
- 依赖该 codoc 的下游节点状态变为 error（断引用）
- 相关的依赖边一并清除

### US-C5 浏览工作区中的 codoc 列表

**作为**用户，**我想**浏览当前工作区所有的 codoc，**以便**找到我要查看或编辑的文档。

**验收标准：**
- 以列表形式展示所有 codoc
- 每个条目显示 path 和状态 badge
- 点击某条目可查看详情

### US-C6 创建只有 meta 的空 codoc

**作为**用户，**我想**创建一个只有标题和描述、暂不含数据的 codoc，**以便**先占位后续再填充内容。

**验收标准：**
- 只含 `meta` 段、不含 `data` 和 `view` 的 codoc 合法
- 节点状态为 idle
- 不参与依赖图求值

### US-C7 codoc 格式错误时获得明确反馈

**作为**用户，**我想**在写了不合法的 YAML 时收到清晰的错误提示，**以便**快速定位和修复问题。

**验收标准：**
- YAML 语法错误时解析失败，节点状态 → error
- 错误信息指出具体的格式问题
- 不影响工作区中的其他 codoc

## 3. 依赖图与引用

### US-R1 查看全局依赖图

**作为**用户，**我想**以可视化的方式看到工作区中所有 codoc 之间的依赖关系，**以便**理解知识的整体结构。

**验收标准：**
- 图中每个节点代表一个 codoc（或字段级节点）
- 有向边表示引用关系（从引用者指向被引用者）
- 节点上展示状态颜色

### US-R2 创建引用型字段

**作为**用户，**我想**让一个 codoc 的字段引用另一个 codoc 的字段值，**以便**在文档之间建立数据依赖。

**验收标准：**
- 在 data 中使用 `$ref: "other.codoc#data.field"` 声明引用
- build 时自动建立字段级依赖边
- resolve 时从上游获取被引用字段的值

### US-R3 循环依赖被拦截

**作为**用户，**我想**在不小心创建了循环引用时收到提醒，**以便**避免死循环。

**验收标准：**
- A 引用 B 且 B 引用 A（或更长的环路）
- build 阶段检测到循环并报错
- 错误信息明确列出环路路径

### US-R4 断引用被检测

**作为**用户，**我想**在引用了不存在的 codoc 或字段时被告知，**以便**修正引用路径。

**验收标准：**
- `$ref` 指向不存在的 path 或字段
- build 阶段报错：目标不存在
- 对应节点状态 → error

### US-R5 跨字段精确引用

**作为**用户，**我想**引用另一个 codoc 中的某个特定字段（而不是整个文档），**以便**实现细粒度的数据组合。

**验收标准：**
- `$ref: "meetings/q1.codoc#data.summary"` 精确获取 summary 字段值
- 依赖图在字段粒度建边（nodeId 格式：`path#data.field`）
- 上游该字段变更时，仅相关下游重新 resolve

## 4. Build 与 Resolve

### US-B1 全量构建

**作为**用户，**我想**对整个工作区执行一次全量构建，**以便**验证所有 codoc 的引用和数据是否正确。

**验收标准：**
- 解析所有 codoc → 提取 AST → 构建依赖图 → 校验引用
- 返回构建诊断：成功数、错误数、警告
- 有错误的节点状态标为 error，其余标为 ready

### US-B2 解析单个节点

**作为**用户，**我想**单独 resolve 某个节点的值，**以便**快速查看某个字段的计算结果。

**验收标准：**
- 传入 nodeId（如 `notes/meeting.codoc#data.summary`）
- 按拓扑序先 resolve 所有上游依赖
- 返回该节点的计算值
- 如上游有 error，本次 resolve 失败并说明原因

### US-B3 增量重建

**作为**用户，**我想**修改一个 codoc 后只重建受影响的部分，**以便**在大型工作区中也能快速得到反馈。

**验收标准：**
- 更新某个 codoc 后自动触发增量重建
- 仅该节点及其下游重新解析和 resolve
- 不受影响的节点保持原状态

### US-B4 上游错误阻断下游

**作为**用户，**我想**在上游节点出错时，下游不会尝试无意义的计算，**以便**获得清晰的错误溯源链。

**验收标准：**
- A 依赖 B，B 状态为 error
- A 不会尝试 resolve
- A 的状态反映"因上游错误而无法计算"

### US-B5 Schema 校验

**作为**用户，**我想**在 codoc meta 中声明字段类型约束后自动校验数据，**以便**保证数据质量。

**验收标准：**
- meta.schema 声明字段类型（如 `summary: string`）
- data 中对应字段值不符合类型时 build 报错
- 错误信息指出哪个字段违反了什么约束

## 5. Chat 多 Agent 对话

### US-A1 创建新对话

**作为**用户，**我想**在工作区中开始一段新对话，**以便**就某个话题与 AI 交流。

**验收标准：**
- 点击"新建对话"后创建 chat thread
- 对话与当前工作区关联
- 对话列表中立即出现新条目

### US-A2 发送消息并获得回复

**作为**用户，**我想**发送一条消息后得到 AI 的回复，**以便**获取帮助或进行讨论。

**验收标准：**
- 输入消息后发送
- AI 回复以流式方式逐字显示（SSE）
- 完成后消息持久化到数据库
- 每条 assistant 消息标注是哪个 agent 回复的

### US-A3 流式实时响应

**作为**用户，**我想**在 AI 生成回复的过程中实时看到文字输出，**以便**不必等待完整回复。

**验收标准：**
- 通过 SSE 接收 `text-delta` 事件
- 文字逐片段渲染到消息气泡中
- 流结束后显示完整消息
- 生成过程中有加载状态指示

### US-A4 @指定某个 Agent 回答

**作为**用户，**我想**通过 @mention 让特定的 agent 来回答我的问题，**以便**获得专业领域的回复。

**验收标准：**
- 消息中输入 `@agent-id` 跳过路由，直接交给目标 agent
- 该 agent 的回复标注其身份
- 如果 @mention 了不存在的 agent，有明确错误反馈

### US-A5 查看对话历史

**作为**用户，**我想**重新打开一个已有的对话后看到完整历史，**以便**回顾之前的讨论。

**验收标准：**
- 从对话列表点击已有 thread
- 加载并展示所有历史消息
- 每条 assistant 消息显示对应的 agent 标识
- 消息按时间顺序排列

### US-A6 修改对话标题

**作为**用户，**我想**给对话起一个有意义的标题，**以便**在列表中快速辨识。

**验收标准：**
- 支持修改 thread 标题
- 修改后列表中即时更新

### US-A7 为对话关联 codoc 上下文

**作为**用户，**我想**选择哪些 codoc 作为本次对话的上下文，**以便**让 AI 基于这些文档进行回答。

**验收标准：**
- 可从工作区的 codoc 列表中选择若干个关联到当前对话
- agent 能读取这些关联的 codoc 内容
- 未关联的 codoc 不会进入 agent 上下文
- 可随时增减关联

### US-A8 为对话配置参与 Agent

**作为**用户，**我想**选择哪些 agent 可以参与当前对话，**以便**控制对话中的专家组合。

**验收标准：**
- 可查看所有可用 agent 列表
- 可为 thread 配置参与者（多对多）
- 配置的 agent 可被路由器调度
- 可随时增减参与者

### US-A9 Agent 操作工作区

**作为**用户，**我想**让 AI 帮我查询或修改工作区中的 codoc，**以便**通过对话完成知识管理操作。

**验收标准：**
- 用户说"列出所有 codoc"→ agent 调用 `listCodocs` 返回列表
- 用户说"查看 xxx.codoc"→ agent 调用 `getCodoc` 返回内容
- 用户说"创建一个 codoc"→ agent 调用 `createCodoc` 创建并触发 build
- 用户说"更新某字段"→ agent 调用 `updateCodoc` 更新并触发增量重建
- tool 调用过程对用户透明（可见 tool-use / tool-result 事件）

### US-A10 对话中的 Agent 静默路由

**作为**用户，**我想**直接看到最合适的 agent 的回复，不需要看到中间的路由过程，**以便**获得流畅的对话体验。

**验收标准：**
- 用户发送消息后，router 在后台决定由谁回答
- 不展示"正在转发给 X"之类的中间消息
- 用户只看到最终 agent 的回复（带有 agent 标识）

## 6. Web UI 交互

### US-U1 三栏布局

**作为**用户，**我想**在 chat 页面中同时看到对话和 codoc 详情，**以便**在讨论的同时参考文档内容。

**验收标准：**
- 左侧为聊天面板，右侧为 codoc 详情面板
- 两栏之间可拖拽调整宽度
- 默认比例约 55:45

### US-U2 Codoc 浏览器

**作为**用户，**我想**在对话中打开一个 codoc 浏览面板，**以便**快速查找和选中要查看的文档。

**验收标准：**
- 以侧边抽屉（Sheet）形式弹出
- 展示完整的 codoc 列表
- 每个条目显示状态 badge
- 点击后右侧面板展示该 codoc 详情

### US-U3 消息中的 Agent 标识

**作为**用户，**我想**在每条 AI 回复上看到是哪个 agent 说的，**以便**区分不同专家的观点。

**验收标准：**
- assistant 消息气泡上显示 agent 名称或图标
- 不同 agent 有视觉区分
- 用户消息不显示 agent 标识

### US-U4 对话列表按日期分组

**作为**用户，**我想**在工作区详情页看到按日期分组的对话列表，**以便**快速找到近期的讨论。

**验收标准：**
- 对话按创建日期分组（今天、昨天、更早等）
- 显示对话标题（或默认标题）
- 点击后进入该对话

### US-U5 状态 Badge 可视化

**作为**用户，**我想**通过颜色直观看到每个 codoc 的状态，**以便**一眼识别哪些有问题。

**验收标准：**
- ready → 绿色
- error → 红色
- dirty → 黄色
- idle → 灰色
- badge 出现在 codoc 列表和详情页中

### US-U6 加载态与骨架屏

**作为**用户，**我想**在数据加载过程中看到占位元素而不是空白，**以便**知道内容正在加载。

**验收标准：**
- codoc 详情加载时展示 skeleton 占位
- 对话加载时有加载指示
- 数据到达后无缝替换占位

## 7. 错误与边界场景

### US-E1 同时多用户访问

**作为**用户，**我想**在多人（或多端）同时访问同一工作区时数据保持一致，**以便**协作不出错。

**验收标准：**
- 一端修改 codoc，另一端刷新后能看到最新内容
- 数据库作为单一数据源保证一致性

### US-E2 大量 codoc 性能

**作为**用户，**我想**在工作区包含大量 codoc（500+）时系统仍能正常运行，**以便**不被规模限制。

**验收标准：**
- build 和 graph 操作在合理时间内完成
- codoc 列表分页或虚拟滚动，不卡顿

### US-E3 网络异常时的提示

**作为**用户，**我想**在 API 请求失败时看到明确的错误提示，**以便**知道是临时问题还是需要处理。

**验收标准：**
- 服务端不可达时展示错误状态而非空白
- SSE 断连时提示并支持重试
- 操作失败时提示具体原因
