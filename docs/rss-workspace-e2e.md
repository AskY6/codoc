# RSS Workspace 端到端可用性验证

## 目的

这份文档不是测试某个函数或接口是否工作，而是用一组完整的人工操作脚本，回答一个更直接的问题：

> 最初“RSS workspace 并不好用”的问题，是否已经被解决？

这里的“解决”不是指代码更优雅，也不是指多了几个 API，而是指一个普通用户能不能顺畅完成 RSS 的核心任务，而不需要理解 `codoc`、文件树、`$source`、prompt engineering 或内部实现细节。

## 核心判断标准

如果以下几点成立，就可以认为问题基本解决：

1. 用户打开 RSS workspace 后，能很快知道下一步该做什么。
2. “刷新 feeds”“更新 digest”“订阅新 feed”是明确动作，而不是靠用户自己发明 prompt。
3. 用户可以直接消费内容，而不是先理解 `sources/*.codoc` 和 `inbox.codoc`。
4. 标记已读、收藏等阅读状态在刷新和重开后不会丢。
5. AI 是增强项，不是核心流程唯一入口。

如果仍然出现下面这些现象，就说明问题没有真正解决：

1. 用户必须先理解 workspace 目录结构才能开始。
2. 用户需要手写 prompt 才能完成刷新、digest、订阅这些高频动作。
3. 首页是空的、弱提示的，用户不知道系统现在能做什么。
4. 阅读状态在刷新后丢失，或者用户不敢点，因为不知道会不会丢。
5. agent 一旦失灵，核心阅读流程就走不下去。

## 测试对象

建议优先测试以下对象：

1. 一个新建的 RSS workspace。
2. 一个已经使用过至少一天、包含若干文章状态变化的 RSS workspace。

建议至少找两类测试者：

1. 熟悉项目的人。
2. 不熟悉 `codoc` 内部实现、只会按产品直觉操作的人。

第二类测试者更重要，因为这次要验证的是“好不好用”，不是“作者自己能不能用”。

## 前置条件

开始前准备好以下环境：

1. 本地可以正常启动 RSS workspace 的 Web UI。
2. 网络可访问公开 RSS 源。
3. 有一个可用的 RSS workspace 模板。
4. 测试时允许创建和删除临时 workspace。

建议使用稳定、公开、更新频率较高的 feed，例如：

1. `https://hnrss.org/frontpage`
2. `https://github.blog/engineering/feed/`
3. `https://react.dev/feed.xml`

如果要从零开始建测试 workspace，可用当前 CLI 流程，例如：

```bash
codoc init rss-e2e --from rss
codoc start rss-e2e
```

如果团队平时使用开发态命令启动，也可以沿用现有流程。关键不是命令本身，而是最后进入的是实际用户会看到的 RSS workspace 界面。

## 记录方式

每次测试都建议记录这四类信息：

1. 从进入 workspace 到完成任务一共花了多久。
2. 用户在哪一步开始犹豫，犹豫了多久。
3. 用户是否需要别人解释 `inbox.codoc`、`sources/`、prompt、scheduler 之类概念。
4. 用户是否能在失败后自己找到下一步，而不是只能问开发者。

建议边测边填一个简单表格：

| 场景 | 是否完成 | 完成时间 | 是否需要提示 | 卡点 |
| --- | --- | --- | --- | --- |
| 首次进入 |  |  |  |  |
| 看今天更新 |  |  |  |  |
| 订阅新 feed |  |  |  |  |
| 标记已读并验证持久化 |  |  |  |  |
| 失败恢复 |  |  |  |  |

## 原始问题到测试场景的映射

这次不要只测“功能有没有”，而要测“原来的痛点还在不在”。

| 原始问题 | 对应测试场景 |
| --- | --- |
| 用户不知道先做什么 | 场景 1：首次进入 |
| 刷新和 digest 主要靠 prompt | 场景 2：看今天更新 |
| 订阅 feed 太绕 | 场景 3：订阅新 feed |
| 阅读状态容易丢 | 场景 4：已读/收藏持久化 |
| agent 失败就卡死 | 场景 5：失败恢复 |
| RSS 价值不清晰 | 场景 6：AI 增强阅读 |

## 测试脚本

### 场景 1：首次进入一个新 RSS workspace

**目标**

验证用户第一次进入时，能否在不理解内部结构的情况下，知道这个 workspace 是干什么的，以及下一步该做什么。

**操作步骤**

1. 创建一个全新的 RSS workspace。
2. 打开 workspace 首页。
3. 不看任何文档，不打开文件树，不进入源文件。
4. 观察测试者是否能在 30 秒内说出：
   - 这里是干什么的。
   - 接下来我应该点哪里。
5. 让测试者自己尝试完成“开始使用”的第一步。

**预期结果**

1. 首页应该直接暴露主任务入口，而不是让用户先理解目录结构。
2. 即使当前没有 digest，也应该明确告诉用户接下来该执行什么动作。
3. 测试者不需要知道 `inbox.codoc`、`sources/`、`$source` 这些词。

**失败信号**

1. 测试者第一反应是去点文件树看有哪些 `.codoc` 文件。
2. 测试者问“我要不要先在 chat 里说一句话？”
3. 首页只有空状态，但没有明确下一步动作。

### 场景 2：查看“今天有什么更新”

**目标**

验证“看今天有什么新内容”是不是一个自然、显式、确定的产品路径，而不是 prompt 技巧。

**操作步骤**

1. 进入一个至少有 2 到 3 个 feed 的 RSS workspace。
2. 不打开 chat，不编辑任何文件。
3. 尝试找到“刷新 feeds”或“更新 digest”的入口。
4. 先执行刷新，再执行 digest 更新。
5. 回到首页，阅读结果。
6. 判断测试者能否在不看源码的前提下回答：
   - 今天有哪些值得读的内容。
   - 系统是否已经刷新过。
   - digest 是刚刚更新的，还是历史内容。

**预期结果**

1. 刷新和 digest 应该是显式动作。
2. 首页应该是消费内容的地方，而不是提示用户去和 agent 对话。
3. digest 结果里应该包含 AI 的筛选或摘要价值，而不是只是把原始文章标题堆出来。

**失败信号**

1. 用户只能通过 chat 输入“what's new today?” 才能继续。
2. 执行刷新后，用户仍然不知道内容是否已经更新。
3. 首页没有清楚区分“没有内容”“还没刷新”“刷新失败”“digest 还没生成”。

### 场景 3：订阅一个新的 feed

**目标**

验证“增加一个信息源”是不是一个正常产品动作，而不是让用户手工维护 codoc。

**操作步骤**

1. 在现有 RSS workspace 中，尝试订阅一个新的 feed，例如 `https://react.dev/feed.xml`。
2. 测试者只能使用 UI 中显式提供的入口，或产品明确引导的操作。
3. 完成后，回到订阅列表或 feed 列表确认订阅是否存在。
4. 立刻执行一次刷新。
5. 检查新 feed 的文章是否进入系统。

**预期结果**

1. 测试者不需要手工创建 `sources/<slug>.codoc`。
2. 系统应该给出订阅成功或失败的明确反馈。
3. 新 feed 加入后，用户能在可见的位置确认它已经生效。

**失败信号**

1. 产品只提供一个半成品 prompt，例如“Subscribe to ”，剩下让用户自己补全并赌 agent 理解正确。
2. 用户需要进入文件编辑器才能完成订阅。
3. 订阅成功后没有明确反馈，用户只能靠猜。

### 场景 4：标记已读 / 收藏，并验证状态持久化

**目标**

验证阅读状态是不是稳定可信。这个场景很关键，因为“状态会不会丢”决定用户敢不敢长期使用。

**操作步骤**

1. 选 3 篇文章。
2. 将其中 2 篇标记为已读。
3. 将其中 1 篇标记为收藏。
4. 记录当前列表顺序和状态。
5. 执行一次 feed 刷新。
6. 关闭 workspace，再重新打开。
7. 回到同一个 feed 或文章列表。
8. 检查这 3 篇文章的状态是否仍然正确。

**预期结果**

1. 已读和收藏状态在刷新后仍然正确。
2. 重开 workspace 后状态仍然正确。
3. 即使文章顺序变化，状态也不能错位到别的文章上。

**失败信号**

1. 状态丢失。
2. 状态错位到另一篇文章。
3. 用户不敢点状态按钮，因为界面没有任何持久化信号。

### 场景 5：失败恢复

**目标**

验证系统在不理想情况下是否仍然“可用”，而不是只在 happy path 上显得流畅。

**操作步骤**

1. 尝试订阅一个无效 feed URL。
2. 观察系统如何反馈错误。
3. 人为让某个 feed 刷新失败，或选择一个当前不可访问的 feed。
4. 再次执行刷新。
5. 观察首页、订阅列表、feed 详情页分别如何表达失败状态。
6. 让测试者自己判断“下一步应该做什么”。

**预期结果**

1. 用户能区分“没有新内容”和“刷新失败”。
2. 系统至少能告诉用户是哪一个 feed 出问题。
3. 失败后仍然能继续阅读已有内容，不会把整个 workspace 变成不可用状态。

**失败信号**

1. 所有失败都被吞成“空状态”。
2. 用户只能靠打开开发者工具或日志猜问题。
3. 一个 feed 出错会阻断整个工作区的主要阅读路径。

### 场景 6：AI 增强阅读，而不是接管基础操作

**目标**

验证 AI 是否回到了正确位置：负责总结、筛选、深挖，而不是替代所有基础动作。

**操作步骤**

1. 先完成场景 2 到场景 4，证明不靠 chat 也能完成基础 RSS 使用。
2. 然后再进入 chat，提出一个需要 AI 发挥价值的问题，例如：
   - “这周和 React Compiler 相关的文章里，哪些最值得读？”
   - “帮我把今天关于 AI engineering 的内容整理成 3 条要点。”
3. 检查返回结果是否建立在 workspace 已有内容之上。
4. 如果产品有写回 digest 或 topic note 的能力，验证结果是否落盘到合适的位置。

**预期结果**

1. AI 的作用是摘要、筛选、研究，不是基础导航。
2. 就算不用 chat，用户也已经能完成核心阅读流。
3. 用了 chat 之后，结果应该增强已有工作区，而不是只在对话里飘过。

**失败信号**

1. 不先用 chat，就几乎什么都做不了。
2. AI 回答和 workspace 状态脱节。
3. AI 只给对话回复，不增强 RSS 产品本身。

## 通过标准

为了避免“感觉比以前好一点”这种模糊判断，建议直接用下面的阈值：

### 可以判定“核心问题已解决”

满足以下全部条件：

1. 场景 1 到场景 4 全部通过。
2. 测试者在核心路径上不需要理解 `codoc` 文件结构。
3. 测试者在核心路径上不需要自己发明 prompt。
4. 失败场景下，用户仍然知道下一步该做什么。

### 可以判定“有改善，但问题没彻底解决”

满足以下条件：

1. 场景 1 到场景 4 中，大部分可以完成。
2. 但某些核心动作仍然依赖 chat 或文件编辑。
3. 或者状态持久化、失败恢复还不可靠。

### 可以判定“问题基本没解决”

出现以下任一情况：

1. 新用户第一次进入仍然不知道从哪里开始。
2. 看今日更新仍然主要依赖 prompt。
3. 订阅 feed 仍然需要理解 `sources/*.codoc`。
4. 已读/收藏状态在刷新或重开后不可信。

## 建议执行顺序

如果时间有限，按这个顺序执行最有价值：

1. 场景 1：首次进入
2. 场景 2：看今天更新
3. 场景 3：订阅新 feed
4. 场景 4：状态持久化
5. 场景 5：失败恢复
6. 场景 6：AI 增强阅读

前四个场景决定“RSS workspace 作为产品是否成立”；后两个场景决定“它是否足够稳，且 AI 放在了正确位置”。

## 测试后的复盘问题

每轮测试结束后，建议统一回答这几个问题：

1. 测试者第一次困惑发生在哪一步？
2. 测试者是否主动提到“我是不是得和 agent 说句话”？
3. 测试者是否主动进入文件树，而不是留在主阅读界面？
4. 哪个核心动作最像“工程实现”，而不像“产品动作”？
5. 如果只允许下一轮改一件事，应该改哪里？

如果这些问题已经大多消失，说明最初的“RSS workspace 并不好用”已经从根上得到缓解。
